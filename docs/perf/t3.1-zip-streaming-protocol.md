# T3.1 ZIP 端到端流式组装协议设计

> 所属里程碑：M4 · 性能优化主线
> 状态：**设计草案 · 待实施**

## 0. 背景与动机

当前 SL1/VDT 导出路径（[`conversion-controller.ts`](../../apps/slicer-app/src/core/conversion-controller.ts)）的数据流：

1. 主线程为每层分发编码任务到 worker；
2. Worker 调用 WASM `encode_layer` 得到 `compressedData`（Uint8Array）+ `crc32` + `uncompressedSize`，整块通过 `postMessage` 回传（零拷贝 ArrayBuffer transfer）；
3. 主线程把 `ZipPreparedEntry` 写入 `preparedEntries[layerIndex]`；
4. **全部层就绪后**调用 [`assembleZipArchive`](../../apps/slicer-app/src/core/zip-archive.ts)：遍历 `preparedEntries` 写 local header + data，再写中央目录 + EOCD，最后 `sink.finish()`。

**内存峰值 ≈ 输出大小**（VDT 1380 层场景下约 91 MB）。这在低端移动设备上接近 OOM 红线。

目标：将峰值内存降为 `O(workers × chunk)`，并行度与吞吐量不下降。

---

## 1. 数据流对比

### 1.1 当前数据流

```
worker_k ──(complete layer N, transfer ArrayBuffer)──► main (preparedEntries[N])
...
(all N layers ready)
main ──► assembleZipArchive ──► sink.write(local_header + data) × N
                              ──► sink.write(central_dir + EOCD)
                              ──► sink.finish()
```

峰值：`Σ compressedData.length` 常驻内存。

### 1.2 目标数据流（流式 assemble）

```
worker_k ──(layer N ready, transfer)──► main
main 维护 inFlightBuffer[index→entry] + nextToFlush 指针
while (inFlightBuffer[nextToFlush] exists):
  flush(nextToFlush)  # local_header + data + (optional) data descriptor → sink
  推送 central_descriptor 到延迟队列
  nextToFlush += 1
(all flushed)
main ──► sink.write(central_dir from 延迟队列)
      ──► sink.write(EOCD)
      ──► sink.finish()
```

峰值：`乱序窗口 × compressedData 平均大小 + Σ central_descriptor_metadata`。

- 乱序窗口上界 ≈ `workerCount`（正常情况）。
- Central descriptor 仅含元数据（name + crc + sizes + offset，≈ 60 B/层），1380 层 ≈ 80 KB，可忽略。

## 2. ZIP 格式细节

ZIP 文件线性结构（PKZip AppNote 4.x）：

```
<local_header_1><data_1>[data_descriptor_1]
<local_header_2><data_2>[data_descriptor_2]
...
<central_directory_header_1>...<central_directory_header_N>
<EOCD>
```

**关键点**：local header 里含 `crc32 + compressedSize + uncompressedSize`。若编码时这些值未知（streaming write），必须设置 `general purpose bit flag` 的 **bit 3**（data descriptor 存在），并把 local header 中三者填 0，在 data 后追加 12（或 16，zip64）字节 data descriptor：

```
| signature(optional, 0x08074b50, 4B) | crc32 (4B) | compressedSize (4B) | uncompressedSize (4B) |
```

对于本次设计，**我们预先知道 crc32 和 sizes**（worker 已算好整块 payload），因此可以选择两种实现路径：

| 方案                                    | 需 data descriptor | 复杂度 | 可否支持 worker-side chunked encode    |
| --------------------------------------- | ------------------ | ------ | -------------------------------------- |
| **A. Flush-window + 完整 local header** | ✗                  | 低     | 否（必须 worker 一次返回完整 payload） |
| **B. Flush-window + data descriptor**   | ✓                  | 中     | 是                                     |

**M4 T3.1 范围选方案 A**：worker 仍一次性返回完整 compressed payload（保持现有 `encode_layer` 契约），仅改主线程的 flush 时机。

> 方案 B 留作 T3.3 / T3.5 的后续选项（若 Rust 侧改为 `encode_layer_into` chunked sink）。

## 3. Worker ↔ 主线程协议变更

### 3.1 当前消息

[`WorkerZipLayerPreparedMessage`](../../apps/slicer-app/src/types.ts)（不变）：

```ts
{
    type: "zip-layer-prepared";
    index: number;
    name: string;
    data: ArrayBuffer; // transferable
    compressionMethod: 0 | 8;
    crc32: number;
    uncompressedSize: number;
    computeMs: number;
}
```

### 3.2 T3.1 方案 A：不改协议

Worker 侧零改动；仅主线程 `conversion-controller.ts` 与 `zip-archive.ts` 调整：

- 新增 `ZipStreamAssembler` 类（见 §4）维护 `nextToFlush` + `pendingBuffer: Map<index, ZipPreparedEntry>`；
- `assembleZipArchive` 拆分为三个阶段：
    1. `beginStream(sink, metadataEntries)` — 立即写 metadata 条目（header/config.ini 等已在分发层计算完毕，可立即 flush）；
    2. `pushLayer(entry)` — 入 buffer；若 `entry.index === nextToFlush`，循环 flush；
    3. `finalize()` — 写中央目录 + EOCD，调用 `sink.finish()`。

### 3.3 未来方案 B（T3.3+，非本里程碑）

预留消息类型，**本里程碑不落地**：

```ts
interface WorkerZipLayerStreamBeginMessage {
    type: "zip-layer-stream-begin";
    index: number;
    name: string;
    compressionMethod: 0 | 8;
}

interface WorkerZipLayerStreamChunkMessage {
    type: "zip-layer-stream-chunk";
    index: number;
    data: ArrayBuffer; // transferable
}

interface WorkerZipLayerStreamEndMessage {
    type: "zip-layer-stream-end";
    index: number;
    crc32: number;
    compressedSize: number;
    uncompressedSize: number;
    computeMs: number;
}
```

主线程语义：

- 收到 `begin(index=N)` 时必须 `index === nextToFlush`（streaming 要求严格按序分发；不满足时 stall 等待）；
- `begin` 后立即写 local header（`generalPurposeBitFlag |= 0x08`，crc/sizes 填 0），进入"正在写 N 的 payload"状态；
- 收到 `chunk(index=N)` 直写 sink；
- 收到 `end(index=N)` 写 data descriptor（`0x08074b50 + crc32 + compressedSize + uncompressedSize`），推进 `nextToFlush`。

**一致性**：central directory 的 crc/sizes 仍使用正确值（即便 local header 填 0），读取方按 AppNote 应优先信任 central directory。

## 4. 主线程 API 草案（方案 A）

### 4.1 `ZipStreamAssembler`（替代 `assembleZipArchive`）

```ts
// apps/slicer-app/src/core/zip-stream-assembler.ts
export class ZipStreamAssembler {
  constructor(private readonly sink: OutputSink);

  /** 立即 flush 一个已 prepared 的条目（metadata 用）。 */
  async writePreparedEntry(entry: ZipPreparedEntry): Promise<void>;

  /**
   * 按 index 排序的层入队 + 自动 flush。
   * 调用方不必按序调用；内部按 index 升序 flush。
   */
  async pushLayerEntry(index: number, entry: ZipPreparedEntry): Promise<void>;

  /** 写中央目录 + EOCD。 */
  async finalize(): Promise<ZipArchiveBuildResult>;
}
```

内部状态：

```ts
private nextLayerFlushIndex = 0;
private pending = new Map<number, ZipPreparedEntry>();  // 未按序到达的层
private centralDescriptors: ZipCentralDescriptor[] = []; // 延迟到 finalize
private localOffset = 0;
```

`pushLayerEntry` 逻辑：

```ts
async pushLayerEntry(index, entry) {
  if (index < this.nextLayerFlushIndex) throw new Error("out-of-order layer replay");
  if (index === this.nextLayerFlushIndex) {
    await this.flushEntry(entry, this.layerName(index));
    this.nextLayerFlushIndex += 1;
    // 尝试 flush 后续已暂存的连续段
    while (this.pending.has(this.nextLayerFlushIndex)) {
      const next = this.pending.get(this.nextLayerFlushIndex)!;
      this.pending.delete(this.nextLayerFlushIndex);
      await this.flushEntry(next, this.layerName(this.nextLayerFlushIndex));
      this.nextLayerFlushIndex += 1;
    }
  } else {
    this.pending.set(index, entry);
  }
}
```

`flushEntry` = 写 local header + data，推一条 central descriptor 到 `centralDescriptors`。
`finalize()` = 写中央目录 + EOCD，`sink.finish()`。

### 4.2 `conversion-controller.ts` 改动要点

```diff
- const preparedEntries = new Array<ZipPreparedEntry>(metadataPrepared.length + input.totalLayers);
- preparedEntries.splice(0, metadataPrepared.length, ...metadataPrepared);
+ const assembler = new ZipStreamAssembler(input.sink);
+ for (const meta of metadataPrepared) {
+     await assembler.writePreparedEntry(meta);
+ }

  ...
    if (message.type === "zip-layer-prepared" && message.index === layerIndex) {
-       preparedEntries[metadataPrepared.length + layerIndex] = { ... };
+       await assembler.pushLayerEntry(layerIndex, {
+           name: message.name,
+           compressionMethod: message.compressionMethod,
+           compressedData: new Uint8Array(message.data),
+           uncompressedSize: message.uncompressedSize,
+           crc32: message.crc32,
+       });
        ...
    }
  ...
- const finalizeResult = await assembleZipArchive(preparedEntries, input.sink);
+ const finalizeResult = await assembler.finalize();
```

注意：

- `pushLayerEntry` 是 async（内含 `sink.write`）；handler 必须 `await` 再执行 `dispatch(worker)`，否则下一层分发可能引起 worker 积压。实际调度：分派可以不等 flush，因为 flush 只涉及 sink 写入（快），而下一层编码可以并行；但若 sink 是背压型（`streaming-writer.ts` 的 WritableStream），handler 内应 `await assembler.pushLayerEntry(...).then(() => dispatch(worker))`。
- 老 `assembleZipArchive` 保留为 legacy（可在测试中继续使用），但 `conversion-controller.ts` 默认走 assembler。

## 5. 内存与性能模型

| 指标                          | 当前                              | T3.1 后（方案 A）                                                         |
| ----------------------------- | --------------------------------- | ------------------------------------------------------------------------- |
| 峰值 compressed data 常驻     | `Σ size`（≈ 91 MB / 1380 层 VDT） | 乱序窗口 ≈ `workerCount × avgLayerSize`（典型 4 worker × 66 KB ≈ 260 KB） |
| 峰值 central descriptor 常驻  | 无（直接用 entries）              | `N × ~60 B`（1380 层 ≈ 80 KB）                                            |
| `assembleZipArchive` 阻塞时间 | 全部层完成后串行遍历写            | 分摊到每层收到后即写，finalize 仅写中央目录（80 KB）                      |
| 吞吐                          | 受最后 assemble 时段制约          | 编码与写入重叠，理论加速                                                  |

**验收基线**（plan.md §4 T3.1）：VDT 91 MB 场景峰值内存从 ≈ 输出大小降为 `O(workers × chunk)`。

## 6. 风险与边界

| 风险                                        | 对策                                                                                                                                                     |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pushLayerEntry` async 失败（sink 抛异常）  | 抛至 `reject(error)`；`dispatch` 链检测到 signal.aborted 退出；不再调用 `finalize()`                                                                     |
| 取消（`signal.aborted`）时已 flush 部分条目 | `sink.finish()` 不调用，上层应丢弃输出文件（与当前行为一致）                                                                                             |
| 乱序窗口异常变大（某 worker 长时间 stall）  | `pending.size` 可以加日志/监控；必要时降级：若 `pending.size > threshold`，将未到达的后续层 dispatch 退避，迫使并行度收敛                                |
| 旧版 `assembleZipArchive` 使用方（测试）    | 保留不动；新路径用新 API                                                                                                                                 |
| 中央目录字节级一致性                        | 方案 A 不改字节格式（local header 和 central directory 都完整填写），生成的 ZIP 应与原始 `assembleZipArchive` 逐字节一致。用 `diff` 对比旧输出作为强验收 |

- T3.2 改 sl1/vdt 层的 `compressionMethod` 从 8 → 0（stored），直接减少 `preparedEntries[i].compressedData` 的 CPU 消耗与大小差异。对本协议无字节级影响，只影响 local header 里 `compressionMethod` 字段和 payload 内容。

## 11. 补丁记录（2026-04-17）

本节由 `docs/superpowers/plans/2026-04-17-t3-1-tail-finalize-metric-and-sink.md` 的 Task 1 / Task 3 / Task 5 落地后回填。

### 11.1 `finalizeOnlyWallMs` 指标拆分

原协议 §3 `ZipAssemblyTimings` 只有 `prepareWallMs / finalizeWallMs / totalWallMs` 三字段，落地后发现 `finalizeWallMs` 从 `ZipStreamAssembler` 构造时刻起算，与 layer 阶段几乎完全重叠（8.77s ≈ layers 8.74s），无法用来判定架构计划 §4 "assemble wall-clock ≤ 1.0s"。Task 1 commit `ce37189` 的做法：

- 新增必填字段 `finalizeOnlyWallMs`，严格测量"`finalize()` 入口 → `sink.finish()` 返回"的墙上时间；
- 保留 `finalizeWallMs` 为 `totalWallMs` 的向后兼容别名，避免打破既有日志/埋点；
- `ZipStreamAssembler.finalize()` 在 `runExclusive` 回调内部捕获 `finalizeStartedAt`，落盘后计算并填充；
- legacy `assembleZipArchive` 由于整函数即 finalize 阶段，两字段赋相同值。

验证：bench `pnpm bench:app` 测得 `finalize-only` 中位 **30.3ms**，远低于 1.0s 目标。

### 11.2 第三档 sink 回退：`StreamingResponseSink`

原协议假设 `OutputSink` 只需 `BlobOutputSink`（全内存）与 `StreamOutputSink`（File System Access API 直写磁盘）两档。实际中 Safari、Playwright headless 等环境两者都不具备 FS Access API，会一律回落到 `BlobOutputSink`，永远达不到 §4 "峰值内存 O(workers × chunk)" 的目标。

Task 3 commit `01b7057` 新增 `StreamingResponseSink`：内部用 `TransformStream<Uint8Array, Uint8Array>` + `new Response(readable).blob()`，`write(chunk)` 直接 `writer.write(chunk)`、不在 JS 侧持有 `Uint8Array[]`。首 chunk 懒缓冲以保留 `patchHeader` 语义（对 `ZipStreamAssembler` 不触发，兼容 `assembleBinaryOutput` 的首写场景，但不支持多 write 后的 patch——已明确文档化）。

> **注**：`StreamingResponseSink.finish()` 最终仍返回 Blob，故最终 peak heap 接近 `BlobOutputSink`；它的主要价值是路径与 `StreamOutputSink` 对齐，并为将来接入 Service-Worker streaming download 预留入口。真正 O(workers × chunk) 的内存剖面仍依赖 `StreamOutputSink`。

### 11.3 `ConversionStatusInput.finalizeOnlyMs` 穿透

`use-converter-controller.ts` 把 `zipResult.timings.finalizeOnlyWallMs` 透传到 `buildConversionStatusMessage`，后者在原有 `assemble Xs` 之后追加 `; finalize-only Xs`（可选字段，未提供则省略，向后兼容）。bench harness 的状态解析器支持 `ms`/`s` 双单位归一化。

### 11.4 §4 验收口径勘误

架构计划 §4 T3.1 条目已于 2026-04-17 附加口径勘误段，明确 "`Assemble wall-clock ≤ 1.0s`" 统一按 `finalizeOnlyWallMs` 计量；"峰值内存 O(workers × chunk)" 目标的有效验证路径仅为桌面 Chromium 手动跑（`showSaveFilePicker` 可触发）或引入 headed Playwright fixture——bench harness 本身在 headless 下不具备验证能力。
